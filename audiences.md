# ThinkRail — целевые аудитории и что мы для них деливерим

> Рабочий документ (черновик, не узел спек-графа). Разделение «сейчас / могли бы» сверено с кодом:
> `goal-and-requirements.md`, `architecture.md`, спеки `pi-spec-graph` / `pi-thinkrail-workflow`,
> методы провода в `packages/contracts`.

Структурная ремарка: в исходной диаграмме смешаны три оси — **роль** (продакт, программист),
**умение читать код** (вайб-кодер) и **тип организации** (стартап, PET). Из-за этого сегменты
пересекаются. Ниже исходные узлы сохранены, добавлены недостающие, а в конце — приоритизация по
одной оси: «кто уже чувствует боль недоверия к агенту и платит».

## B. Что могли бы деливерить

Пометки: **[Ф]** — есть фундамент, дешёвое расширение; **[С]** — средне; **[Д]** — далеко/новая
подсистема. **★** — сильно дифференцирует от Cursor / Claude Code.

### 1. Спек-слой

- Спека как артефакт / source of truth / точка синхронизации **[Ф]**
- Markdown + его диффы как «язык программирования с тулингом» ★ **[С]**
- SDD UX: task-oriented спеки, задачи из спек, статус реализации **[С]**
- Pre-build approval: утвердить спеку/план до кода ★ **[С]**
- Drift detection: код разошёлся со спекой ★ **[Д]**
- Живой граф: редактирование, канвас, зависимости решений **[Д]**
- Покрытие: какая часть кода описана спеками, где белые пятна ★ **[Д]**
- Спека как исполняемое ограничение для агента (не только контекст) ★ **[Д]**
- Доки/онбординг-материалы, генерируемые из графа **[С]**

### 2. Контроль над агентом = доверие

- Agent-written code review: второй агент ревьюит изменения первого ★ **[С]**
- Дифф «на уровне намерения», а не строк; «что реально поменялось для пользователя» ★ **[С]**
- Проверка «диф соответствует спеке» ★ **[Д]**
- Лёгкий откат на лету: чекпоинты, откат одного изменения/тула, а не всей ветки ★ **[С]**
- Semantic git: коммит привязан к спеке/таске, история читается намерениями ★ **[Д]**
- Аудит-трейл: решение → спека → код → коммит **[С]**
- Политики/песочница: что агенту можно, что нельзя **[С]**

### 3. Workflow / процесс

- Расширение семейства скиллов (review, refactor, migrate, debug, ship) **[Ф]**
- Конфигурируемые пайплайны, свои воркфлоу пользователя **[Д]**
- Автоматизации/триггеры (по push, по CI, по расписанию), headless-режим **[Д]**
- Self-improvement: агент копит правила проекта из твоих правок **[Д]**

### 4. UX / платформа

- All-in-one: редактор + git + терминалы + агент + спеки — **уже есть [Ф]**
- Оркестрация нескольких агентов по worktree, сравнение вариантов ★ **[С]**
- Remote/телефон через Tailscale: «дать добро агенту из метро» **[Ф]**
- Cost ledger, бюджеты, per-step routing (дешёвая модель на рутину) **[С]**
- Коммит/пуш/ветки из UI, интеграция PR / Checks / Review **[С]**
- Превью/деплой результата (для не-кодеров) **[Д]**
- Не-pi агенты — архитектурно закрыто (решение «pi only»); фиксируем как явный trade-off

### 5. Команда / организация

- Общий спек-граф команды, ревью спеки как PR **[Д]**
- Мультиюзер / сервер / auth / SSO **[Д]** — сейчас хост однопользовательский и без auth
- Метрики процесса: доля агентного кода, откаты, drift rate, время до мержа **[С]**
- On-prem / приватность / свои модели (угол JetBrains) **[С]**

## C. Аудитории

### 1. PET-проекты / индивидуалы

- **Боль:** проект умирает на 40%; вернулся через две недели — агент не помнит контекст
- **Сейчас:** бинарь в одну команду, всё в одном окне, `starting-a-new-project`
  (интервью → `goal-and-requirements.md`), спек-граф как память проекта между сессиями
- **Могли бы:** «продолжи с того места» по спеке, шаблоны проектов, откат в клик, мобильный доступ
- **+** огромный объём, легко попробовать, терпимы к сырому, вирусны
- **−** почти не платят; retention завязан на жизнь проекта; **боль спек у них минимальна** —
  весь проект помещается в голове

### 2. Маленькие команды / стартапы (2–15)

- **Боль:** скорость важнее всего, но агентный код копит хаос; онбординг человека и агента;
  доки не пишут никогда
- **Сейчас:** параллельные worktree, спеки лежат в их репо (не в чужом SaaS), общий набор
  workflow-скиллов, per-project trust
- **Могли бы:** спека как точка синхронизации между людьми и агентами, review агентных изменений,
  drift, командный граф, метрики, semantic git
- **+** есть бюджет и быстрое решение; боль реальная; спека = дешёвая замена процессу, которого у них
  нет; хороший LTV; естественный апсейл в аудитории 8/9
- **−** «мы не пишем доки» — надо доказать, что спека не тормозит; для команды нужен мультиюзер,
  которого нет; конкуренты бесплатны и «и так работают»

### 3. Pi-community

- **Боль:** pi — это CLI; хочется вкладки, редактор, диффы, историю
- **Сейчас:** практически весь V1 — это оно; плюс `pi-spec-graph` / `pi-visualize` как портируемые пакеты
- **Могли бы:** галерея/шаринг скиллов и расширений, headless/CI-режим, «UI для pi» как отдельный дистрибутив
- **+** нулевой CAC (они уже это ищут), отличные баг-репорты и контрибуции, канал дистрибуции
- **−** сегмент крошечный; OSS-мышление (не платят); **риск платформы**: судьба продукта = судьба pi;
  их запросы (CLI-фичи) тянут в сторону от продукта

### 4. Продакты и менеджеры

- **Боль:** не могут проверить, что сделали то, что просили; спека в Notion врёт через неделю;
  влиять можно только через разработчика
- **Сейчас:** честно — **почти ничего**. Мы показываем им Monaco, терминалы и git; Specs-таб read-only
- **Могли бы:** спека как их родной артефакт (правят Markdown, не код), approval до реализации,
  диффы спеки вместо диффов кода, задачи из спек, статус «реализовано / дрифтануло»,
  мобильное «утвердить»
- **+** самая большая недообслуженная боль и максимальный отрыв от Cursor/Copilot; они держат бюджет;
  спека — их язык, а не наш компромисс
- **−** нужен **другой вид приложения** (не-IDE); они не будут ставить бинарь и логиниться в провайдера;
  риск «ещё один Jira/Notion»; продажа в организацию длинная

### 5. Программисты, которые всё меньше хотят читать код

- **Боль:** агент пишет быстрее, чем можно прочитать; ревью — узкое место; страшно мержить
- **Сейчас:** Changes/diff, изоляция по worktree, планы/todo/tool-cards, вопрос агенту по графу «где это»
- **Могли бы:** agent-review, дифф на уровне намерения, «соответствует ли спеке», точечный откат,
  чек-лист рисков, semantic git
- **+** самый быстрорастущий сегмент; платят, потому что это их работа; боль новая и по-настоящему
  нерешённая; **ровно наш дифференциатор**
- **−** очень конкурентно; высокая планка (они умеют сравнивать); «агент ревьюит агента» надо доказать
  метриками, иначе воспринимается как игрушка

### 6. Вайб-кодеры (не читают код)

- **Боль:** сломалось — непонятно почему и как вернуть
- **Сейчас:** worktree-изоляция (ветку можно выбросить) — но UX всё ещё требует понимания git;
  по сути мы им пока не подходим
- **Могли бы:** откат в один клик, состояние проекта человеческим языком, спека как единственное,
  что они читают и пишут, автоматические чекпоинты, превью/деплой
- **+** большой растущий рынок, платят за «не сломать», спека — их естественный интерфейс
- **−** мы показываем им IDE — это отталкивает; конкуренция с Lovable/Replit/Bolt, у которых есть
  хостинг и превью; дорогая поддержка; деплой далеко от нашей архитектуры

### 7. Power AI users

- **Боль:** гоняют несколько агентов, упираются в оркестрацию, контекст и стоимость
- **Сейчас:** параллельные сессии, worktrees, выбор модели/thinking, скиллы, шаблоны, статистика токенов
- **Могли бы:** оркестрация и сравнение вариантов, per-step routing, cost ledger/бюджеты,
  автоматизации, headless/cron, remote с телефона
- **+** ранние адоптеры, платят за инструмент, громкие в соцсетях, дают фронтир-фидбек
- **−** сегмент мал и непостоянен (меняют инструмент раз в месяц); их запросы не масштабируются на
  массу — риск построить продукт под 200 человек

## Аудитории, которых в диаграмме не было

### 8. Тимлиды / инженерные менеджеры

- **Боль:** команда переехала на агентов, а что реально происходит с качеством — непонятно;
  ответственность размыта
- **Сейчас:** —
- **Могли бы:** метрики (доля агентного кода, откаты, drift), спека как зафиксированная
  договорённость, обязательный approval-гейт, аудит-трейл
- **+** покупают на команду; боль будет только расти
- **−** нужен сервер/мультиюзер; риск восприятия как надзор → сопротивление снизу

### 9. Архитекторы / staff+ инженеры  ← *лучший идеологический фит*

- **Боль:** их решения не доживают до кода; влияние не масштабируется
- **Сейчас:** спек-граф, `writing-specs`, спеки в репо
- **Могли бы:** drift detection, спека как ограничение для агента, граф зависимостей решений,
  ревью спеки как PR
- **+** это чемпионы внедрения внутри компаний; продукт буквально про них
- **−** их мало; привередливы к формату; долгий цикл

### 10. Легаси / модернизация

- **Боль:** систему никто не понимает, агент без карты опасен
- **Сейчас:** `importing-a-codebase` → первый спек-граф, Specs как карта
- **Могли бы:** авто-граф по большой кодбейзе, покрытие спеками, safe-change, миграции по спеке
- **+** дорогая боль, реальные бюджеты, мало конкурентов
- **−** пределы на больших репо, долгие пилоты, требования on-prem

### 11. Enterprise / регулируемые отрасли (угол JetBrains)

- **Могли бы:** трассируемость решение→код, аудит-лог агента, on-prem/свои модели, политики, SSO
- **+** платят много; бренд и канал JetBrains; спек-слой — готовый ответ на «как вы контролируете ИИ»
- **−** длинный цикл, комплаенс, нужен мультиюзерный сервер — сейчас хост локальный и без auth

### 12. Solo-founders / indie hackers (отделить от PET)

- **Боль:** надо довезти продукт, а не поиграться; один человек за всю команду
- **Сейчас:** весь V1
- **Могли бы:** спека вместо отсутствующих продакта и архитектора, мобильный контроль, автоматизации
- **+** платят (это их бизнес), высокий retention, отличные истории
- **−** чувствительны к цене; любят «всё в одном» с деплоем

### 13. Агентства / консалтинг / фриланс

- **Сейчас:** проекты/воркспейсы, быстрый вход в чужой код
- **Могли бы:** спека как ТЗ и отчёт клиенту, шаблоны, «что сделано»
- **+** платят из проектного бюджета, интенсивное использование
- **−** фрагментированы, живут в инструментах клиента

### 14–16. Слабые / поздние (упомянуть, но не целить)

- **OSS-мейнтейнеры:** + видимость и дистрибуция · − не платят, и агентные PR — боль, которую мы
  скорее усилим
- **QA:** тест-кейсы и приёмка из спек · − чужой инструментальный мир
- **Образование / буткемпы:** спека учит проектному мышлению, сильный канал JetBrains · − денег нет,
  цикл длинный

## D. Приоритизация

| Горизонт | Кто | Почему |
|---|---|---|
| **Beachhead — уже попадаем** | Pi-community, Power users, «программисты, которые всё меньше читают код» | Продукт подходит **без переделки**; CAC ≈ 0; они генерируют доказательства ценности |
| **Следующая волна — главный доход** | Маленькие команды/стартапы, solo-founders, архитекторы | Требует agent-review, откат, approval, drift, коммит/PR — всё в слое «контроль», который и так наш дифференциатор |
| **Развилка — нужен продуктовый выбор** | Продакты, вайб-кодеры | Требуют **другого UI** (не-IDE) и/или деплоя. Это отдельный продукт поверх того же хоста, а не фича |
| **Позже / через партнёров** | Тимлиды, enterprise, легаси | Требуют мультиюзер + auth + аудит — новая подсистема |
| **Не целить сейчас** | OSS, QA, техписатели, образование | Не платят или не наш вход |

**Главный вывод.** Список «что могли бы» на две трети — про **доверие к агенту** (agent-review, откат,
semantic git) и **спеку как контракт**. Это же и есть ось выбора аудиторий: целиться в тех, кто **уже
потерял контроль над агентом**, а не в тех, кто ищет удобный UI. UI скопируют за квартал, спек-слой и
контроль — нет.
